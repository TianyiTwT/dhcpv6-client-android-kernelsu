# 设计说明

记录本模块中几处不直观的取舍。实现细节见对应文件内的注释。

## 收发为什么走 AF_PACKET

Android 自身的 DHCPv6 客户端会在无线接口上占用 UDP 546，而该 socket 已绑定到
只监听 ff02::1:2 的地址，外部进程无法复用。模块把收发下沉到 AF_PACKET 二层，
自行构造并过滤以太帧，从而绕开端口占用。代价是校验和需要自行计算，且 IPv6
UDP 校验和写回时必须经过 `htons()`；遗漏这一步的症状是请求有去无回，很容易被
误判为服务端不支持 IA_NA。

BPF 过滤器用于把非 DHCPv6 帧在进入用户态之前丢弃，使空载下不产生唤醒。过滤的
判据中 next header 位于 IPv6 头的偏移 20（不是 6）。不使用 libpcap。

## 为什么需要看门狗

Android 自身的 DHCPv4 由 `IpClient` / `ConnectivityService` 监督，但该监督者只
服务于框架自己启动的客户端。本模块的 `dhcp6c` 不是由框架启动的，因此整条生命
周期都没有人管：

| | 框架的 DHCP 客户端 | 本模块的 `dhcp6c` |
| --- | --- | --- |
| 何时启动 | 网络需要地址时由框架启动 | 需要看门狗 |
| 何时停止 | 网络消失时由框架停止 | 需要看门狗 |
| 重连 / 漫游 | 框架重建客户端 | 需要看门狗 |
| 地址归属 | 写入 `LinkProperties`，框架保管 | 框架不认，会被当作未知地址清除 |
| 进程退出 | 框架负责拉起 | 需要看门狗 |

`wide-dhcpv6` 自身也不监听链路事件。该仓库没有任何 `PF_ROUTE` / `RTM_*` 处理，
只在启动时经 `ifinit()` 读取一次接口信息，主循环仅 `select()` 于 DHCPv6 socket。
因此它不知道 Wi-Fi 重连、不知道地址被网络栈清除，只能等 75 分钟一次的 T1 续租，
而那时旧地址已不存在，续租必然失败。

`scripts/dhcp6c-watchdog.sh` 补的就是这一层。该角色在 BSD 上由 rc 脚本承担，
Android 没有对应钩子。

### 轮询，而不是监听事件

设备上没有可用的 netlink 事件工具：toybox 的 `ip` 不支持 `monitor`，busybox 的
`ip` 只接受 `address|route|link|neigh|rule`。因此直接读 `/proc/net/if_inet6`，
用 shell 内建 `read` 解析，不 fork 任何进程，5 秒一次的巡检开销可忽略。

### 判据：盯住具体地址的消失

判据是「上一次取得的地址是否还在接口上」，而不是「地址集合是否发生变化」。
后者看似更通用，实际会自我激发：`dhcp6c` 添加地址这个动作本身就会改变集合，
于是看门狗重启 `dhcp6c`、`dhcp6c` 重新添加地址、集合再次变化，形成无限重启。
盯住某个具体地址则没有这个问题，因为地址出现不触发重启，只有消失才会。

## 停止时不发送 RELEASE

停止走 `SIGUSR1`，启动时并带 `-n`，两者都使 `dhcp6c` 在退出时不发送 RELEASE。
地址稳定性依靠 DUID 与 IAID 不变来保证，而发送 RELEASE 等于告知服务端该地址已
归还，可能被回收并分配给其他主机。保留租约并令其自然超时，重新 Solicitation
时更容易取回原地址。DHCPv6 的租约本身是软状态，不发送 RELEASE 完全合规。

需要区分「不发送 RELEASE」与「保住本地地址」，这是两件事。进程退出时
`release_all_ia()` → `remove_ia()` → `cleanup_addr()` →
`na_ifaddrconf(IFADDRCONF_REMOVE)`（`dhcp6c_ia.c:441`、`addrconf.c:228/284`）
仍会删除本地地址，这条路径不受 `opt_norelease` 影响。这是有意为之：用户点击
停止后，接口上不应留下没有协议守护的地址。不发送 RELEASE 保的是服务端的租约
绑定，使下次拉起能迅速取回同一地址；真正让地址在重启前后保持一致的是 DUID 与
IAID 都未改变。

## 并发保护

状态变更由 WebUI、`action.sh`、看门狗三处独立触发。`d6_start` 在启动前必须
删除 pidfile，因为 `dhcp6c` 会对它加 `flock`，残留的旧 PID 会让它误判「已有实例
在运行」而直接退出；而删除操作会替换 `flock` 赖以生效的 inode，于是两个并发的
`d6_start` 可以各自创建新 inode、各自获得锁，导致同时启动两个实例。

因此所有状态变更都在一个 `mkdir` 原子锁内串行化，等待上限 10 秒；超过上限则
认定持有者异常退出并强行接管一次，避免永久卡死。

### `stop` 与 `hold`

`stop` 的语义是「置暂停标志 + 结束看门狗」。看门狗内部不能使用它：看门狗遇到的
都是暂时性状况（接口尚未出现、模块被停用），必须能自动恢复，而 `stop` 会让看门狗
下一拍进入待命并结束自身，再也无法恢复。开机时 Wi-Fi 通常尚未就绪，看门狗第一拍
即撞上「接口不存在」，症状就是「重启后客户端不自启，手动点一次才恢复」。

因此新增 `hold`：只停止客户端，不置暂停标志、不结束看门狗。看门狗的两个分支
均改用 `hold`，同时 `service.sh` 在开机时清除上一次会话残留的暂停标志——
暂停是运行期状态，跨重启没有意义。

## 状态短语的判定顺序

`lib/common.sh` 的 `d6_status_short()` 依次判定，先排除本就不该工作的原因，
最后才报告工作结果：

| 条件 | 显示 |
| --- | --- |
| 模块被停用 / 待卸载 | 已停用 |
| 用户手动暂停 | 已暂停 |
| 接口不存在（未连接 Wi-Fi） | 未连接 Wi-Fi |
| 接口存在但未 up | Wi-Fi 未就绪 |
| 上一次取得的地址仍在接口上 | 已获取 IPv6 地址 |
| 客户端在运行但尚无地址 | 正在获取 IPv6 地址 |
| 客户端未运行 | 客户端未运行 |

判据使用「上一次取得的那个地址是否还在」，而不是「是否存在全局地址」：运营商
RA 下发的地址会让后者为真，那时无法判断本模块是否成功。

### 写回 `module.prop` 的几点约束

管理器每次打开模块列表都会重新读取 `module.prop`，因此该文件被直接用于显示
当前状态，无需管理器专有接口，KernelSU 系与 Magisk 均适用。

- 静态文案不另存文件，而是每次从当前 `description` 中剥离 `【…】` 前缀得到。
  模块更新后 live 目录被替换为新解包的副本、`description` 回到静态版本，这样
  可以自动恢复；若另存一份到 `state/`，两边迟早不一致。
- 状态未变化时不写文件。看门狗每 5 秒调用一次，绝大多数时候状态相同，此时只做
  一次纯内建的读取，否则模块目录的 mtime 会持续变化。
- 先写同目录临时文件再 `mv`。rename 是原子的，管理器不会读到写了一半的
  `module.prop`。
- 刷新时机：开机（`service.sh`）、每 5 秒（看门狗）、点击「操作」按钮
  （`action.sh`），也可手动执行 `dhcp6c-ctl.sh desc`。管理器不会主动感知变化，
  需要重新打开模块列表或下拉刷新。

## 为什么需要显式参数

启动 `dhcp6c` 时下列参数缺一不可：

- `-f` 前台运行。否则它会自行 `daemon(0,0)`，从 shell 看是命令立刻返回，
  日志也会被交给 syslog，在 Android 上走 logd，文件日志丢失。
- `-p <pidfile>` 必须显式指定。编译期 `DHCP6C_PIDFILE` 为 `/var/run/dhcp6c.pid`，
  Android 上不存在该目录，而该文件即使在 `-f` 模式下也会被无条件打开，
  打开失败进程直接退出。同理需要 `-p` 才能在不存在的 `/var/run` 下运行。
- `-d` 把日志级别提到 `LOG_INFO`。默认阈值是 `LOG_WARNING`，
  Solicit / Reply / 地址增删等关键过程一条都不会记录。使用 `-d` 而非 `-D`：
  后者是 `LOG_DEBUG`，噪声更大且对诊断没有额外帮助。

## DNS 为什么不在本模块内

服务端下发的 DNS 只记录到 `state/dns.servers`。Android 10 起没有设置系统解析器
的公开接口：`setprop net.dns1/2` 已不被 netd 读取，`ndc resolver` 命令已被移除
（Android 16 实测返回 `500 0 Command not recognized`），netd 的 resolver AIDL
受 `NETWORK_STACK` 权限保护，root shell 无法调用。

因此自定义 DNS 由独立模块实现，机制是在 `nat/OUTPUT` 上用 DNAT 改写目的地。
本模块只负责取得地址，不介入 DNS。
